# Smart Planner P1A Placement Explanations Design

**Status:** Awaiting written-spec review  
**Date:** 2026-08-06  
**Repository:** `NguyenDukKyeon/smart-planner`  
**Stack base:** P0 exact head `3e296b2d2bb1e7f52b482643a30496b4e3757c0a`  
**Implementation branch:** `improve/p1a-placement-explanations`

## 1. Goal

Make the Today study flow explain why every lesson or review appears, while preserving the compact daily workflow.

P1A adds two related capabilities:

1. a pure, reusable placement-reason model for lessons and reviews;
2. persistent metadata for the most recent manual date move, so the explanation survives reload.

The primary user-facing outcome is one short reason badge per Today item, with an optional detail disclosure showing the latest manual move when relevant.

## 2. Scope

P1A includes:

- persistent provenance for the most recent manual lesson move;
- provenance writes for every Move action in Flexible Schedule, including drag-and-drop, previous-day, next-day, and date-picker moves;
- safe removal of provenance when schedule date or schedule mode is changed through the lesson editor;
- pure derivation of placement reasons for fixed lessons, manually moved lessons, capacity-carried flexible lessons, normal roadmap progression, and reviews;
- one primary reason badge on each Today lesson or review card;
- optional secondary detail for the latest manual move;
- safe sanitization of malformed provenance;
- undo and reload behavior covered by tests;
- focused regression coverage for the Today integration.

P1A does not include:

- storing the full history of lesson moves;
- redesigning the whole Today card system;
- Flexible Schedule filtering or capacity-workspace redesign;
- the full Course Manager ownership refactor;
- changing review intervals or review generation;
- adding a new dependency;
- merging P0 or P1A automatically.

## 3. Approved product decisions

The owner approved these rules:

- provenance persists across reload;
- only the most recent manual move is stored;
- editing `scheduledDate` or `scheduleMode` through the lesson editor clears provenance;
- editing title, topic, duration, XP, or subject without changing date or mode keeps provenance;
- every calendar Move action records provenance, not only drag-and-drop;
- one primary reason is shown on the card;
- fixed-current-state reasoning outranks historical manual-move reasoning;
- manual-move history appears as secondary detail when another current-state reason has higher priority.

## 4. Data model

Add an optional field to `Lesson`:

```ts
export type LessonPlacementProvenance = {
  kind: "manual-move";
  movedAt: string;
  fromDateISO: string;
  toDateISO: string;
};

export type Lesson = {
  // existing fields
  placementProvenance?: LessonPlacementProvenance;
};
```

### Field semantics

- `kind` is fixed to `manual-move` for forward compatibility.
- `movedAt` is an ISO-8601 date-time string generated by the application.
- `fromDateISO` is the lesson date immediately before the Move action.
- `toDateISO` is the target date selected by the Move action.
- a later Move replaces the previous provenance object.
- the provenance object belongs to the catalog lesson and is persisted with the catalog.

### Validity rules

A provenance object is valid only when:

- `kind === "manual-move"`;
- `fromDateISO` is a valid ISO calendar date;
- `toDateISO` is a valid ISO calendar date;
- `fromDateISO !== toDateISO`;
- `movedAt` parses as a valid ISO date-time.

Invalid provenance is removed while the lesson itself remains intact.

## 5. Persistence and sanitization

The catalog remains the source of truth for placement provenance.

### Stored catalog

Catalog normalization must explicitly sanitize `placementProvenance` rather than relying on unknown-property preservation. A valid object is retained. An invalid object is omitted.

### External import

CSV and JSON import paths must not accept user-supplied provenance. Import continues to accept only the documented lesson fields. This prevents imported files from impersonating application-generated move history.

### Existing data

No destructive migration is required. Existing lessons without provenance are valid and are interpreted as having no known manual-move history.

### Export and backup

Because provenance is part of the normalized catalog lesson, ordinary catalog backups and exports retain valid provenance. Undo snapshots also retain it automatically.

## 6. Move semantics

`buildMoveLessonDateCandidate` is the canonical place that creates manual-move provenance.

For a successful move from one date to another, it updates both fields in one candidate:

```ts
{
  scheduledDate: targetDateISO,
  placementProvenance: {
    kind: "manual-move",
    movedAt: clock().toISOString(),
    fromDateISO: previousDateISO,
    toDateISO: targetDateISO,
  },
}
```

The builder receives an injectable clock or `movedAt` value so tests are deterministic.

### No-op move

Moving a lesson to its existing date is a no-op:

- no provenance is created or replaced;
- no persistence occurs;
- no undo entry is added.

### Transaction behavior

The P0 transaction boundary persists the date and provenance together. If persistence fails:

- React state is not published;
- the old date remains visible;
- the old provenance remains visible;
- no undo entry is added.

### Undo

P0 full-snapshot undo restores both `scheduledDate` and the previous provenance object. This covers:

- restoring no provenance after the first move;
- restoring an older provenance object after a second move;
- restoring provenance cleared by an editor operation when that operation is routed through the shared transaction owner in a later package.

## 7. Editor clearing rules

`updateLessonDetails` gains explicit provenance handling.

Clear provenance when the editor actually changes either:

- `scheduledDate`; or
- `scheduleMode`.

Keep provenance when the patch changes only:

- title;
- topic;
- duration;
- XP;
- subject placement or topic placement.

Supplying the same date or same mode is not considered a schedule change and does not clear provenance.

The clearing rule applies to editor-style schedule changes. Calendar Move actions use the move candidate builder and therefore replace provenance rather than clearing it.

## 8. Placement-reason model

Create a pure module:

```text
src/lib/lesson-placement.ts
```

Core types:

```ts
export type LessonPlacementReasonKind =
  | "fixed-today"
  | "manual-move"
  | "carried-from-earlier-date"
  | "next-in-roadmap"
  | "review-due";

export type ManualMoveDetail = {
  fromDateISO: string;
  toDateISO: string;
  movedAt: string;
};

export type LessonPlacementReason = {
  kind: LessonPlacementReasonKind;
  label: string;
  description: string;
  manualMove?: ManualMoveDetail;
  reviewAgeDays?: number;
};
```

The module is pure. It does not import React, browser storage, toasts, or component code.

### APIs

```ts
export function deriveLessonPlacementReason(params: {
  lesson: Lesson;
  assignedDateISO: string;
}): LessonPlacementReason;

export function deriveReviewPlacementReason(params: {
  ageDays: number;
}): LessonPlacementReason;
```

The scheduler does not need a new parallel metadata store. Consumers already know the assigned day from the queue or plan day, while `lesson.scheduledDate` remains the earliest eligible date for flexible lessons and the exact date for fixed lessons.

## 9. Primary-reason precedence

The reason badge represents current placement first and historical context second.

### Lesson precedence

1. **Fixed today**
2. **Manually moved to this assigned date**
3. **Carried from an earlier eligible date because of capacity**
4. **Next in roadmap**

### Review reason

Reviews use **Review due after X days** and do not compete with lesson reasons.

### Exact derivation rules

#### Fixed today

Use when:

- `scheduleMode === "fixed"`; and
- `scheduledDate === assignedDateISO`.

Label:

> Cố định hôm nay

Description:

> Bài cố định đã được đặt vào lịch hôm nay.

A valid manual move remains available as secondary detail.

#### Manual move

Use as the primary reason when:

- provenance is valid;
- `placementProvenance.toDateISO === assignedDateISO`; and
- the fixed-today rule did not match.

Label:

> Đã chuyển thủ công

Description:

> Bạn đã chuyển bài sang ngày này.

#### Carried from an earlier date

Use when:

- the lesson is flexible; and
- `assignedDateISO > scheduledDate`.

Label:

> Dời vì ngày trước đầy

Description:

> Ngày đủ điều kiện trước đó không còn đủ công suất nên bài được chuyển sang hôm nay.

If provenance exists but its target is earlier than the assigned date, the capacity-carried reason remains primary and the manual move remains secondary history.

#### Next in roadmap

Use as the fallback for an ordinary flexible lesson selected on its earliest eligible date.

Label:

> Tiếp theo trong lộ trình

Description:

> Đây là bài tiếp theo chưa hoàn thành trong thứ tự học hiện tại.

#### Review due

Use the existing review age supplied by the scheduler.

Label:

> Ôn sau X ngày

Description:

> Bài đến lượt ôn theo mốc nhắc sau X ngày.

### Manually added lessons

P1A does not emit a separate `manually-added` reason because the current catalog has no trustworthy creation-origin field. Guessing from IDs or titles is prohibited. A future package may add creation provenance explicitly.

## 10. Today component architecture

Create:

```text
src/components/today/LessonPlacementReason.tsx
```

Responsibilities:

- render one compact primary badge;
- expose an accessible disclosure control;
- render the primary description;
- render the latest manual-move detail when available;
- format dates and move time for Vietnamese display;
- work without hover on touch devices.

`TodayLessonCard` receives a derived value:

```ts
placementReason: LessonPlacementReason;
```

It does not infer placement rules itself.

`TodayPanel` derives reasons from queue items and passes them to cards. Review cards use `deriveReviewPlacementReason`.

### Disclosure behavior

Use one disclosure pattern on desktop and mobile instead of separate hover-only behavior.

Collapsed state:

- one colored reason badge;
- a compact “Chi tiết” affordance with `aria-expanded`.

Expanded state:

```text
Tại sao bài này xuất hiện?

Bài cố định đã được đặt vào lịch hôm nay.

Lần chuyển gần nhất:
Từ 05/08/2026 → 06/08/2026
Lúc 10:24
```

Only one reason badge is visible. Secondary history is never rendered as a competing badge.

## 11. Error behavior

### Malformed provenance

- strip the malformed field during normalization;
- retain the lesson and all valid schedule fields;
- do not block application startup;
- do not display manual-move text.

### Failed move persistence

- keep previous date and provenance;
- show the existing actionable transaction error;
- do not append undo history.

### Missing explanation context

- never guess manual movement;
- use `next-in-roadmap` for an ordinary flexible lesson when no stronger reason is provable;
- reviews always use their existing age metadata.

## 12. Testing strategy

### Pure data tests

- valid provenance is retained by catalog normalization;
- malformed kind, dates, equal dates, or invalid `movedAt` are removed;
- external import cannot inject provenance;
- existing lessons without provenance remain unchanged.

### Move candidate tests

- first move creates provenance;
- second move replaces the previous record;
- no-op move does not replace provenance;
- an injected clock produces deterministic `movedAt`;
- persistence failure publishes neither date nor provenance;
- undo restores the previous date and previous provenance.

### Editor tests

- changing date clears provenance;
- changing schedule mode clears provenance;
- supplying the same date or same mode keeps provenance;
- changing title, topic, duration, XP, or subject placement keeps provenance.

### Reason derivation tests

- fixed today wins over manual move;
- manual move is primary when its target equals the assigned date;
- carried-from-earlier-date wins when the scheduler assigns later than the move target;
- ordinary flexible work uses next-in-roadmap;
- reviews show the correct age label and description;
- malformed or missing provenance never produces manual-move text.

### UI regression tests

- Today cards receive a placement reason;
- exactly one primary badge is rendered per item;
- the detail disclosure is keyboard accessible;
- manual move detail appears only when valid;
- mobile behavior does not depend on hover.

### Verification gates

```bash
npm run typecheck
npm run lint
npm test
npm run build
git diff --exit-code
```

All commands must pass on the exact implementation head. Existing non-blocking warnings must be reported rather than silently represented as fixed.

## 13. Acceptance criteria

P1A is complete when:

- every Today lesson and review displays one truthful primary reason;
- a manual move survives reload;
- all Flexible Schedule Move methods create the same provenance shape;
- a second move replaces the first record;
- editor date or mode changes clear provenance;
- unrelated lesson edits keep provenance;
- fixed today remains the primary reason even after a manual move;
- a flexible lesson assigned after its earliest date explains capacity carry-forward;
- review labels use the existing 1/3/7/14/30-day age;
- malformed provenance is removed without losing the lesson;
- failed persistence cannot leave date and provenance out of sync;
- undo restores the complete previous state;
- typecheck, lint, tests, build, and clean-tree verification pass;
- the P1A PR remains stacked on P0 until P0 is accepted or the branch is deliberately rebased.

## 14. Spec self-review result

- No placeholders or unresolved requirements remain.
- Current-state reason precedence and historical detail are separated consistently.
- The design avoids a new scheduler metadata store because assigned date is already available to consumers.
- Manual-add origin is explicitly excluded because it cannot currently be derived reliably.
- P1A remains one bounded implementation package and does not absorb the wider P1 roadmap.
